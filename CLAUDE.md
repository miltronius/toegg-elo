# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

TöggELO (Töggeli Elo) - a dashboard to track 2v2 table soccer (foosball) matches and rank players using the Elo ranking system.

## Commands

### Frontend (run from `frontend/`)
```bash
pnpm dev        # Start dev server on port 5173
pnpm build      # Production build
pnpm lint       # ESLint on src/
pnpm test       # Vitest unit/component tests (run once)
pnpm test:watch # Vitest in watch mode
pnpm preview    # Preview production build
```

### Supabase Edge Function (run from `supabase/functions/calculate-elo/`)
```bash
deno lint       # Lint the function
deno test -A    # Run tests
```

### Releases (run from repo root)
```bash
pnpm changeset   # add a changeset to your PR (see .changeset/README.md)
```

### Pre-commit hook
Husky runs `pnpm lint && pnpm test` (frontend) and `deno lint && deno test -A` (edge function) on every commit.

### Environment Setup
Copy `frontend/.env.example` to `frontend/.env.local` and fill in:
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

## Architecture

### Stack
- **Frontend:** React 19 + Vite + TypeScript, Recharts for Elo history charts, `d3-force-3d` for the relationship graph's 2D/3D layout math (rendering is our own SVG), `@react95/core` for Win95 theme chrome, `react-i18next` for translations
- **Backend:** Supabase (PostgreSQL + Auth + RLS)
- **Edge Function:** Deno (`supabase/functions/calculate-elo/`) for Elo computation
- **Package manager:** pnpm

### Frontend Structure
- `frontend/src/lib/supabase.ts` - all Supabase queries and mutations; single source of truth for data access
- `frontend/src/contexts/AuthContext.tsx` - wraps the app, exposes `useAuth()` with user, role, `myPlayerId` (the player this account has claimed, read from its own `player_accounts` row; `refreshMyPlayer()` re-reads it after a claim) and auth methods. `useMe()` returns just role + `myPlayerId` and, unlike `useAuth`, doesn't throw outside a provider - it's what components that only *mark* things ("(you)", rename rights) use, so they still render in isolation; their tests `vi.mock` it
- `frontend/src/contexts/ThemeContext.tsx` - exposes `useTheme()` with `theme` (`"light" | "dark" | "win95"`) and `setTheme()`; persists selection in cookie `toegg-theme` (1-year); sets `data-theme` on `<html>` synchronously to avoid flash
- `frontend/src/lib/i18n.ts` - i18next init (imported once in `main.tsx`); components call `useTranslation()` for `t()`. English (`en`, fallback) + German (`de`), with strings in `frontend/src/locales/{en,de}.json`; language persisted in cookie `toegg-lang` via `i18next-browser-languagedetector` (detection order cookie → browser, `de-CH` normalized to `de`). Also exports `DATE_LOCALE` (`'de-CH'`) - the fixed locale every `toLocale*String` date/time call uses, so dates stay Swiss-formatted (dd.mm.yyyy) regardless of UI language. Achievement names/descriptions are translated at the display layer under the `achievementDefs.<id>` keys (the `ACHIEVEMENT_DEFINITIONS` in `achievements.ts` stay English as the shared backend source + fallback)
- `frontend/src/App.tsx` - main orchestrator; fetches all state in one TanStack Query (`fetchAppData`, key `["appData", userId, role]`) and refetches via `refresh()` (`invalidateQueries`), passes data + callbacks to children; manages `selectedSeason` shared across Leaderboard, Teams, and PlayerDetail
- `frontend/src/lib/teamUtils.ts` - pure team stat computation (`computeTeamStats`, `teamColor`, `teamKey`); no DB calls
- `frontend/src/lib/achievements.ts` - `ACHIEVEMENT_DEFINITIONS` array; shared between frontend and the `_shared` edge function. Goal achievements count goals with `teamGoals` (mirrored in both files): an empty goal field falls back to 10 for the game's winner and 0 for its loser, and a pre-series match (`games` null) counts as 10:0. That fallback is only for **totals**. Flawless Victory/Fatality need both fields typed in, so a winner-only or half-filled game never counts as a shutout. Pair tiers carry `meta.partnerId` (the key the Achievements card reads for "with X"). **Per-season achievements** (`season_participated`, `season_top_1/2/3/5/10`, `season_net_positive`) carry `seasonId` → `player_achievements.season_id` and can be held once per season. Placements come from `computeSeasonPlacements` over the stored `player_season_stats` of **ended** seasons: rank among ranked players (`RANKED_MIN_GAMES`) by season Elo, ties share a rank, nothing below 5 ranked players, a Top N needs more than N, best tier only, dated `ended_at`. In the Green (ranked, ≥ 1501) sits outside that ladder, and On the Board (3rd game of a season) comes from matches. Metas count **distinct ids**, rarity counts **players** holding an id, and the lists group repeats (×N, seasons in the tooltip). `recomputeAllAchievements` reads links, seasons and standings itself, or takes them pre-read (`AchievementPreRead`) - the admin Recompute reads them before its delete. Ending a season runs a non-destructive recompute (`endSeasonAndStartNew` → `recomputeAchievements`), since it never goes through `calculate-elo`
- `frontend/src/lib/rosterFilter.ts` - who counts as "part of the season": a player is **ranked** only at `RANKED_MIN_GAMES` (3) games in the season in scope. `filterRoster(players, "all" | "played" | "ranked")` drives the Leaderboard's roster toggle (table *and* both charts, since they all consume the same filtered list). The two narrowing views are gated on how much they'd actually show - `isFilterAvailable` offers one at `FILTER_MIN_ENTRIES` (1) player, `defaultRosterFilter` auto-selects the narrowest at `AUTO_SELECT_MIN_ENTRIES` (4 - a 2v2 match *is* 4 players, so the played view takes over from the very first recorded game), else falls back to `all`. So a view is never *entered* empty and never *defaults* to a board too thin to read. `resolveRosterFilter` drops a pinned choice that has no data in the current scope (e.g. switching to a season where nobody qualifies) rather than stranding the user on an empty board behind a disabled button. Callers pass season-scoped players (Leaderboard overrides `matches_played` with the season's wins+losses), so the same helper serves season and all-time views. **The toggle is season-only**: `rosterFiltersFor(isSeasonView)` fixes all-time to `all` (ranking is a per-season idea, and all-time the only players without a game are ones added and never used, so there's nothing worth narrowing). The Leaderboard still renders the toggle there, disabled and locked on All, so the header doesn't reshuffle when switching between a season and all-time. `defaultRosterFilter`/`resolveRosterFilter` take that list, so a pin carried over from a season falls back. In a season's `all`/`played` view the Leaderboard table marks ranked players with a 🏅 badge (`isRanked`); not under `ranked`, where every row would carry it, and never all-time. Badges (🏅, and the 🔥/🥶 streak, which share a column since a current streak is one or the other) sit in their own narrow columns between rank and name, so they align whatever the name lengths; each column only appears when a visible row fills it. No DB calls
- `frontend/src/lib/seasonStats.ts` - pure headline-stat computation (`computeSeasonStats`): games played, active players, longest win/lose streak, best/worst day, biggest win/loss, highest/lowest Elo (season-normalized for a season, raw all-time otherwise), busiest day, win-rate leader, achievements unlocked, games-by-weekday, per-day activity + date range; no DB calls
- `frontend/src/lib/relationshipGraph.ts` - pure league-wide relationship computation (`computeRelationshipGraph`): nodes = players who played, friend edges = games as teammates, foe edges = games as opponents. Foe records are directional on an undirected `lo:hi` key - always stored from `lo`'s side, with `loShare` (0..1) driving the tug-of-war split. `topEdgesPerPlayer` keeps each player's N strongest links and drops the rest; **an absolute "min games" threshold does not work here** - with ~12 players everyone eventually partners with and faces everyone, so the graph is complete (all C(n,2) pairs) at any realistic match volume. Filters edges only, never nodes. No DB calls. Overlaps `computeTeammateCounts`/`computeOpponentCounts` (`achievements.ts`) and the private `computeHeadToHead` (`PlayerDetail.tsx`) - those are per-player, this is league-wide; consolidating them is open work
- `frontend/src/lib/playerLinking.ts` - pure rules for account ↔ player links. `canRenamePlayer(player, me)`: an admin renames anyone, the linked owner their own player, any `user` a player nobody has claimed - for the real *and* anonymous name. **UI-only until #118**: the backend still lets any `user` update `players` directly. `canClaimPlayer` mirrors `claim_player` (unlinked `user`/`admin`, unclaimed player). `linkErrorKey` maps the codes the link RPCs raise (`player_already_linked`, ...) to `linking.errors.*`. No DB calls
- `frontend/src/components/ClaimPlayerDialog.tsx` - the "This is me" confirm (`modal-panel`, so Win95 needs nothing). Portalled to `<body>` - opened from inside PlayerDetail's `.modal-panel`, whose children Win95 gives side margins, it would otherwise leave undimmed strips - while React still bubbles its clicks through PlayerDetail's panel, whose `stopPropagation` keeps them from closing PlayerDetail too. A refused claim keeps it open with the reason
- `frontend/src/lib/seasonAwards.ts` - Season Awards voting (#121; the tally and winners are #122). `SEASON_AWARDS` is the six fixed awards in ballot order (names translated under `seasonAwards.awards.<id>`; the ids are also the `award_id` CHECK and `cast_award_vote`'s list). **The window** (`awardVotingWindow`/`awardVotingStatus`): opens at the earliest of `voting_opened_at` ("Open voting now"), `planned_end_at − AWARD_VOTING_LEAD_DAYS` (7) and `ended_at` - so every season gets a vote even with no planned end - and closes at the admin's `voting_closes_at` if set (earlier or later than the default), else `AWARD_VOTING_TAIL_DAYS` (14) after the next season (`number + 1`) starts. `votingStatusLabel` turns that into the one status line ("Open until …", "Closed …", "Opens …") the season info row and the admin block share. Half-open `[opens, closes)`, mirrored by `award_voting_is_open` in SQL, which writes the days as `168`/`336 hours` because the TS works in ms and a days INTERVAL follows DST. `awards_finalized_at` (#122) wins over the clock. Status is a pure function of `(data, now)` - a window opening changes nothing in the DB, so the nudge ticks every 60s. **Eligibility** (`eligibleNomineeIds`, mirrored by `award_nominee_eligible`) reads `player_season_stats` wins + losses, the count the 🏅 badge and placements use: `ranked` = `RANKED_MIN_GAMES`+, `rookie` = ranked now and never ranked in an earlier season. (A seventh, "Special Guest" for 1-2 games, was withdrawn before release; restore it from git history if wanted.) It is live (a running season changes it), so the server re-checks every vote and #122 again at the close. `ballotAccess(me)`: `vote` for a linked `user`/`admin`, `link` for an unlinked one, `none` for viewers/visitors (a demoted linked account included - the RPC refuses it). `parsePlannedEnd` wraps `parseSwissDateTime` with the after-start CHECK; `awardErrorKey` maps the RPC codes to `seasonAwards.errors.*`. No DB calls
- `frontend/src/components/AwardVoteNudge.tsx` - "🗳️ Vote for the Season Awards", one per season whose ballot is open (two overlap only if a new season's voting is opened within two weeks of its start), with `x/6 picked` and the close date ("14 days into the next season" while the season still runs). App builds it once and passes it as a `ReactNode` slot (`awardNudge`) into Timeline and SeasonDialog → SeasonStats. In Season Stats it **ignores the scope select**, so a just-ended season's ballot isn't hidden behind the default running-season scope. Unlinked `user`/`admin` get a muted "link your player" hint instead; viewers and visitors see nothing
- `frontend/src/components/AwardBallotDialog.tsx` - the ballot: an overview of six `AwardCard`s (your pick, votes cast so far; a disclosure via `aria-expanded`, opening on the first award you haven't picked in) above the open award's grid of `NomineeCard`s (`role="group"` labelled by the award), plus an "X of Y players have voted" line. Nominees are limited to who qualifies right now, never your own player, each showing season Elo and games. **Each pick is saved as it's made** (no submit), which is what makes picks changeable until close and any award skippable (clicking the picked card again clears it). A refused save reverts the picker and shows why. A pick who stopped qualifying stays visible with a warning rather than blanking - blanking would hide that the vote is at risk. Portalled to `<body>` at `z-[1100]`, above SeasonDialog (`z-[1000]`), which it can open from. App renders it only once the votes query has loaded, or it would open blank and read as "no picks"
- `.shiny-card` (App.css) + `hooks/useTilt.ts` + `lib/tilt.ts` - the ballot's "shiny card", shared by `AwardCard` and `NomineeCard` (a toggle button, `aria-pressed`): it turns to face a mouse cursor, with a holographic sheen, a specular highlight and a border glow following it; `.is-glowing` (the picked nominee, the open award) gets a spinning conic-gradient border (`@property --shiny-spin`; without `@property` it just holds still), `.is-done` (an award you've picked in) a calm green rim, `.is-stale` a warning one. **The tilt goes to CSS variables (`--rx/--ry/--mx/--my`) on the element, never React state**, so a moving mouse costs no re-render. The box is measured on `pointerenter`, while the card is still flat - measuring per move reads the tilted box and the tilt chases itself. Touch (`pointerType`), `prefers-reduced-motion` and Win95 (raised/pressed button in CSS) get a flat card
- `frontend/src/components/AwardVotingAdmin.tsx` + `SeasonScheduleAdmin.tsx` - the Admin tab's "Season Awards voting" card: one `SeasonScheduleAdmin` block per season whose voting an admin may need to steer - the running season, plus the previous one while its ballot is open (it runs into the first two weeks of the next; ticks every 60s so it drops out on time). Fields (Swiss text, like the banner window): the planned end (running season only) and the closing date; Save sends only the fields that changed, so a stored closing date in the past doesn't block saving the other. Buttons: "Open voting now" (running season, before it opens; one-way - `open_award_voting` keeps the first moment) and "Close voting now" (while open; reversible by setting a later closing date). Both confirm. Each block is a `<details>` whose summary keeps the title and status; it starts open only while that ballot is open. The new-season view (SeasonDialog) takes an optional planned end too. SeasonDialog's info view only *shows* the voting status (one `votingStatusLabel` row) and the vote nudge, at the top above the details and statistics
- "You" highlighting (all via `useMe()`): your Leaderboard row (`row-me`), "(you)" in PlayerAutocomplete, your node in RelationshipGraph, your teams in Teams (`row-me` rows / `team-card-me` cards plus a 🪪 "Your team" badge; in the table it and the 🔥/🥶 streak sit in their own `badge-col` columns before the name, each shown only when a visible row fills it, mirroring the Leaderboard), and `ClaimedMarker` in PlayerDetail (bare 🪪 on someone else's claimed player, a "This is you" badge on yours; both `cursor: help`, since they only carry a tooltip)
- `frontend/src/lib/playerSearch.ts` - pure name-matching for the player picker. `sortPlayersByName` is locale-aware (`DATE_LOCALE`, `sensitivity: "base"`) so umlauts file with their base letter rather than after z; `normalizeForSearch` strips case and diacritics so typing "muller" finds "Müller"; `filterPlayers` returns prefix matches before substring ones, alphabetical within each tier. **Ordering is alphabetical, not by Elo** - the picker is for finding a name you already have in mind, and a list that reshuffles as ratings change has no stable place to look; rank belongs on the leaderboard. No DB calls
- `frontend/src/lib/goals.ts` - goals scored : received (`playerGoalTally`, and `TeamStats.goals` via `computeTeamStats`), counted with the achievements' `teamGoals`. The fallback can only undercount (a winner's empty field is 10, which is exact since games run to 10; a loser's is 0), so a total is a floor, and `exact` is false once any counted game lacks the loser's score. `GoalStatCard` then shows "at least". No DB calls
- `frontend/src/lib/eloHistory.ts` - `didWin`/`didLose`, the one place a win is read off an `elo_history` row. **Never infer it from the sign of `elo_change`** - see the Elo Calculation section. No DB calls
- `frontend/src/components/MatchForm.tsx` - records a **series**, not a single result. The old "Team A wins / Team B wins" buttons are gone; in their place is a list of games, each with two optional goal fields and an A/B winner toggle. Entering two different goal counts derives the winner and locks the toggle - the score is the truth, so a contradiction is unrepresentable rather than merely discouraged. That keeps tapping winners the fast path while scores stay opt-in *per game*, so a session where someone lost count halfway through is still recordable. Key invariants:
  - **The form opens on `DEFAULT_GAME_ROWS` (3) rows, and untouched rows are dropped** (`isBlankGame`). Offering three only works because a 2-0 sweep can leave the third alone instead of having to delete it. A row with *anything* typed in it is not blank and still has to resolve to a winner - half-entered data is a mistake worth reporting, not something to discard silently
  - Submission is blocked until at least one game is recorded, every non-blank game has a winner, and the tally is decisive (a level series has nowhere to go in `winning_team`)
  - Empty goal fields hint `0`, switching to `10` on the side that won the game. Nothing reads the placeholder - it is there so the two fields stop looking interchangeable once a winner is picked
  - The projection chips switch from per-game if-win/if-lose to the actual projected delta as soon as the tally could be submitted, and come from `projectSeries` rather than being scaled locally, since the four deltas round together
- `frontend/src/components/PlayerAutocomplete.tsx` - type-to-find combobox replacing the old `PlayerDropdown` (deleted). Used by MatchForm (4x, with `excludeIds` hiding players already picked) and the Teams player filter (via `emptyLabel` for its "All players" entry). Selection is always by id; the text box only finds it, so text matching nobody selects nobody and the field snaps back to the current selection on Escape/blur rather than leaving a half-typed name looking authoritative. Arrow keys wrap (`nextHighlight`), Enter takes the sole match when nothing is highlighted, Backspace on an empty box clears
- `frontend/src/lib/colors.ts` - palette constants mirroring the CSS vars, plus `hashHue`/`hslHex` (seed string → stable HSL → hex, used by `teamColor` in `teamUtils.ts`) and `RELGRAPH_SLOTS`. Note `Leaderboard.tsx` keeps its own file-private index-based `playerColor` for evenly-spaced bump-chart hues - deliberately different
- `frontend/src/components/RelationshipGraph.tsx` - force-directed player network. Uses `d3-force-3d` for layout math only (it covers both modes via `numDimensions(2|3)`); the SVG is rendered here, so colors stay CSS vars, all three themes work, and the tug-of-war edges keep working. `frontend/src/types/d3-force-3d.d.ts` hand-declares the package (it ships no types). Key invariants:
  - **3D must seed nodes on a sphere** (`seedPosition`): with every z at 0 the repulsion has no z-component and the layout stays flat forever. Switching 2D→3D re-seeds for the same reason
  - Friends|Foes swaps the link set on the *same* simulation so nodes hold position; dimension/data/canvas changes rebuild it
  - `chargeFor()` scales repulsion to the room per node - a fixed charge either knots up on a large canvas or flings nodes off a small one
  - `WARMUP_TICKS` runs the settle synchronously (`tick()` fires no events) so the graph arrives near-settled instead of animating hundreds of rendered frames
  - Projection is one path: 2D is the 3D projection with zero rotation and z = 0, which reduces to identity
  - Nodes are draggable (pointer capture → `fx`/`fy`/`fz` pinning → `alphaTarget(0.3)`); a press that never moves counts as a click. Background drag orbits in 3D, pans in 2D; wheel zooms (registered non-passively by hand, since React's synthetic wheel handler is passive)
  - **Node colour is not identity - the labels are.** No palette of ~12 perceptually distinct colours exists (measured with the dataviz skill's validator: past six, pairs fall under the ΔE 15 normal-vision floor; the old id-hash scheme scored 5.8, i.e. indistinguishable). So the six `--relgraph-c1..c6` vars are assigned by graph colouring (`assignColorSlots`) purely so linked players never match - which is what makes the two-tone foe edges readable. Clean at the default budget; the friend+foe union can force a repeat at budget 5+. Slot → hex lives in CSS, so themes still work without the component knowing the theme
  - Friend edges are **directed**: game counts are symmetric but preference isn't, so `loPicked`/`hiPicked`/`mutual` mark an unrequited favourite with an arrow (one `auto-start-reverse` marker serves both ends)
  - **Your own node** (`useMe().myPlayerId`) gets a `--color-primary` ring and a "(you)" label - a ring rather than a fill, because the fill is the graph colouring above
  - Scopes seasons locally and defaults to all-time, rather than using App's shared `selectedSeason` - so App passes it the **unfiltered** `allPlayerSeasonStats`
- `frontend/src/lib/banners.ts` - pure visibility logic for the scrolling message banner. **Every banner is a row in `banners`, the new-season announcement included** - a `create_season_banner` trigger inserts one whenever a season starts, so an admin can edit, reschedule, retarget or delete it like any other. Visibility is a window (`starts_at`/`ends_at`, either bound optional) gated by `is_active`; keeping the switch separate from the window is what lets an admin park a scheduled message without losing its dates. `bannerStatus` collapses that to `live | scheduled | expired | hidden` for the admin list's chips. Note the switch and the window are **independent controls, not a three-way choice** - an earlier version offered "show now / scheduled / hidden", which read as redundant because hiding and scheduling aren't alternatives: hiding is "never show this", scheduling is "show it between these times", and every combination of the two is meaningful. `audience` (`everyone | members`) splits logged-in from the public landing view - it is *not* a permission tier (every signed-in role sees `members`), and RLS enforces it server-side as well as `forAudience` client-side. A stored row can only hold one language, so a season banner's `message` starts NULL meaning "render the translated default" (`isGeneratedSeasonBanner`); an admin's text overrides it for everyone, and clearing the field reverts. `SEASON_BANNER_DAYS` (14) here is **descriptive only** - the real window is written on the row by the trigger, so it must be kept in sync with that INTERVAL. Every decision is a pure function of `(data, now)` because a window opening changes nothing in the DB, so no realtime event ever announces it. Also holds the marquee pacing constants; `MARQUEE_GAP_RATIO` **mirrors the `60vw` gap in App.css** - one cycle travels exactly one copy, so the two must agree or the scroll speed drifts. No DB calls
- `frontend/src/lib/bannerText.ts` - the one place banner rows meet translation, kept out of `banners.ts` so that stays plain-data only. `bannerDisplayText(banner, seasons, t)` resolves a generated season banner to the translated string and everything else to its stored message; returns `""` when a season banner outlives its season, and callers drop empties rather than render a blank slot between separators. `storedMessage(typed, banner, seasons, t)` is the inverse for the admin form: the form **prefills** a season banner's field with the generated text so it can be edited in place, which makes "saved untouched" indistinguishable from "deliberately retyped the same words" - so text matching the generated default (or blank) stores NULL and stays translated, and only genuinely different text becomes an override
- `frontend/src/components/MessageBanner.tsx` - the marquee itself, rendered for everyone (logged out included) under the header. Everything visible is folded into one strip of text rather than a stack or carousel, so extra messages cost no vertical space. Key invariants:
  - **The strip is repeated three times, not twice.** A cycle shifts the track left by exactly one copy, so the remaining `N-1` have to still cover the screen; at `N=2` that needs one copy to be wider than the viewport on its own, which a short announcement isn't - the right edge goes blank once per cycle. At `N=3` the two 60vw gaps clear it whatever the message length
  - The track is `inline-flex` so it is sized by content; that is what makes `translateX(-100%/3)` land exactly on one copy and hide the seam
  - Only the first copy is exposed to assistive tech; the rest are `aria-hidden`, so an announcement is read once
  - A 30s tick re-evaluates visibility, since a window opening or closing produces no realtime event to refetch on
  - `prefers-reduced-motion` drops to a single static, self-scrollable copy - moving text is a classic vestibular trigger
  - **Easter egg: the strip scratches like a record** (`hooks/useTurntable.ts`). Grab anywhere on the bar and drag, or flick it to spin on before it eases back to normal speed. The CSS animation still runs the strip in normal use; a grab reads its computed `transform`, sets `data-scratching` (which switches `animation-name` off, see App.css) and positions the track by inline `transform`. The hand-back restarts the animation with a negative `animation-delay` so it resumes exactly where the hand or coast left it - that works because removing `animation-name: none` starts a *fresh* animation. `transform` and `animation-delay` are written to the DOM directly and React owns only `animation-duration`, so dragging never re-renders. Hover-to-stop covers the whole bar, not just the strip, so it agrees with the grab area. Off under reduced motion (both the hook and the cursor/`touch-action` CSS)
  - **A release banner's text is a `<button class="banner-link">`** (`data-release-version`) that opens the changelog. Since the turntable grabs on every press, `useTurntable` tells the two apart: a release with under `TAP_SLOP_PX` of travel (`isTap`) is handed to `onTap` with the pressed element, and `onClickCapture` swallows the browser's own click after any grab - otherwise a tap would open twice and a scratch would open once. Keyboard clicks (`detail === 0`) and reduced motion (no grab) go through untouched. The link's padding is cancelled by an equal negative margin so the copy width the loop is paced on doesn't change, and `.banner-marquee` spans the bar's full height so that enlarged target isn't clipped by its `overflow: hidden`
- `frontend/src/lib/turntable.ts` - pure motion math for the banner scratch: offsets along the strip (wrapped per copy), release velocity over the last 80ms (a hand that stopped before letting go releases at 0, so grab-hold-read still works), flick detection relative to normal scroll speed, a real-time exponential coast (refresh-rate independent), and `slipNeedle`, which caps the record's pitch *per second* so a fling slips under the hand instead of squealing into aliasing. No DOM access
- `frontend/src/lib/scratchSynth.ts` - pure audio for the scratch: `synthesizeAhh` builds the classic "ahh" sample (harmonics shaped by vowel formants; silence, vowel, silence, with the needle dropping on the onset), and `renderNeedle` plays it at a signed speed by *chasing a target position* - which is what makes a still hand silent and backwards playback possible. **`renderNeedle` runs in the AudioWorklet as `toString()` source**, so it must not reference anything outside its own body (its constants are declared inside it); `scratchSynth.test.ts` rebuilds it with `new Function` to enforce that
- `frontend/src/lib/scratchAudio.ts` - Web Audio glue: one shared AudioContext created lazily on the first grab (browsers only start audio from a gesture), the worklet loaded from a Blob, a gain for the coast fade, and a suspend two seconds after the record stops. Any failure leaves scratching silent rather than broken. Untested (jsdom has no Web Audio); the math it runs lives in the two files above
- `frontend/src/lib/changelog.ts` - pure parser for the changesets `CHANGELOG.md` (`parseChangelog` → releases → sections by kind → entries with a player-facing `summary`, developer `details`, PR link, author) plus `inlineTokens` for the only inline markdown rendered (`code` and http(s) links - never any other scheme). Accepts bare `- summary` lines and dated headings so hand-written history fits; never throws. No DB calls

### Data Flow
1. `App.tsx` fetches everything through one TanStack Query; mutations call `refresh()` to invalidate it
2. All DB interactions go through helper functions in `supabase.ts`
3. Match recording invokes the `calculate-elo` Deno edge function via `supabase.functions.invoke()`, which sends the signed-in user's session token - the function refuses anyone who isn't a `user` or `admin` (see Auth & Roles)
4. Child components call parent-provided callbacks to trigger data refresh
5. Season Awards votes are the one exception to step 1: their own query (`["awardVotes", userId]`, enabled only for a linked account), so a pick doesn't refetch the dashboard, plus turnout per season (`["awardTurnout", seasonId]`, fetched for the two newest seasons - the only ones whose ballot can be open - so the season list stays clock-free in render). A pick invalidates both. Not realtime

### Auth & Roles
Three roles enforced at DB level via Row-Level Security (RLS):
- `viewer` - read-only (default on signup)
- `user` - can record matches and manage players
- `admin` - full control including deletes and user role management

A `handle_new_user()` trigger auto-creates a `viewer` profile in the `profiles` table on signup. Magic link (OTP) login is supported.

**Policies are dropped by exact name, and permissive ones are OR'd.** `20260203_deletion_policies.sql` created `"Allow public delete on …"` and `20260311_auth_and_roles.sql` dropped `"Allow delete on …"`, so on prod the open policies survived beside the role-based ones - and since any one permissive policy admits a row, the anon key could delete every player, match and history row until 2026-09-16. When replacing a policy, drop it under the name it was actually created with, then compare `pg_policies` on staging and prod rather than trusting the migration files. `anon` holds table-level grants on everything in `public`, so RLS is the only thing in the way.

**`calculate-elo` does its own authorization** (`supabase/functions/calculate-elo/auth.ts`). It writes with the service role, so RLS never sees the caller, and the platform's `verify_jwt` gate is no substitute - it accepts the anon key (a valid JWT with no user behind it) and publishable keys, all of which ship in the bundle. Until 2026-09-16 that meant the anon key could record matches. The handler now resolves the bearer token with `auth.getUser` (the Auth server, not a local JWT decode, so a deleted user's unexpired token is refused) and requires a `user` or `admin` profile - `RECORDING_ROLES` mirrors the "Users and admins can insert matches" policy, so change both together. It runs before the body is parsed. Any future function that writes with the service role needs the same treatment.

**`get_my_role() <> 'admin'` is not an admin check.** `get_my_role()` is NULL for a logged-out caller, `NULL <> 'admin'` is NULL, and `IF` treats NULL as false - while Supabase's default privileges grant EXECUTE on every new `public` function to `anon`. So `end_season_and_start_new` could be called with the anon key until `20260930_season_award_voting.sql`, which re-created it with `COALESCE(get_my_role(), '')` and revoked `anon`. **`set_banner_order` has the same flaw, and `apply_inactivity_penalties` has no role check at all; both are still callable by `anon` pending a hotfix.** Write role checks with `COALESCE`, and `REVOKE ... FROM PUBLIC, anon` on every new client-callable function.

### Database Schema (key tables)
- `players` - name, current_elo (default 1500), matches_played, wins, losses
- `matches` - team_a/team_b player IDs (2v2), season_id, and the series: `team_a_games`/`team_b_games` (the tally that drives the rating) plus `games` JSONB (`[{w, a, b}, ...]` - the winner per game, goals optional and display-only). A level series is rejected by CHECK, so `winning_team` stays NOT NULL and every existing aggregation keeps reading it; a matching CHECK stops it disagreeing with the tally. `games` is NULL on rows recorded before series existed - those were backfilled to a 1-0 tally, which is exactly how they were rated
- `elo_history` - per-match Elo snapshots (elo_before, elo_after, elo_change, `won`, match_id, season_id); inactivity penalty rows have match_id = null. `won` is deliberately nullable with no "match rows must have a result" CHECK: the migration and the edge function deploy separately, so rows written in between have to be accepted (readers fall back to the old sign rule - see `lib/eloHistory.ts`)
- `seasons` - number, name, is_active, k_factor, `partner_weight`, ended_at; only one active season at a time. Historical seasons carry `partner_weight = 0`, which is what they actually ran on
- `player_season_stats` - one row per (player, season): `elo_at_start` (all-time rating when the row was made), `current_season_elo` (normalized, starts at 1500), wins/losses, last_match_at. Rows come from `end_season_and_start_new` for everyone existing at a season start, and from the `on_player_created` trigger for players added mid-season. Before that trigger (2026-09-16) a mid-season player had no row: `calculate-elo` fell back to their all-time rating (the same 1500) so ratings were right, but `increment_season_stats` is a bare UPDATE and silently recorded nothing, leaving them off the season board. The trigger's migration backfilled the season running then; `20260930_backfill_ended_season_stats.sql` did the same for the seasons already over (8 rows on staging, S2/S3), rebuilt from `elo_history`. Writable through RLS only by admins (`deleteMatch` recomputes it from the browser); everything else writes via the service role or SECURITY DEFINER functions
- `player_achievements` - player_id, achievement_id, unlocked_at, `season_id` (NULL = one-time, set = earned in that season); recomputed on every match by the shared achievements function. Unique on `(player_id, achievement_id, season_id)` **`NULLS NOT DISTINCT`** (PG 15+), so one-time rows still dedupe - any `ON CONFLICT` on this table must name all three columns (the upserts and `link_player_account` do). **Release order** for `20260930_season_achievements.sql`: migration, then `calculate-elo`, then the frontend; in between, the old function's upsert names a key that no longer exists and fails (non-fatally - the match still records)
- `profiles` - linked to `auth.users`, stores role
- `player_accounts` - `player_id` PK, `user_id` UNIQUE, `linked_at`: one account ↔ one player (#117). A table of its own rather than a `profiles` column, so `get_players()` can expose `is_linked` without saying *which* account. **No write policies** - every write goes through SECURITY DEFINER RPCs: `claim_player` (caller `user`/`admin`), `admin_link_player` and `unlink_player` (admin). Only `user`/`admin` accounts can be linked, by either route; demoting a linked account keeps the link. Reads: your own row, admins all. The RPCs raise bare codes (`not_allowed`, `account_not_eligible`, `account_already_linked`, `player_already_linked`, `player_not_found`, `not_linked`) as the message. Two traps they guard against: `get_my_role()` is NULL for a logged-out caller and `NULL NOT IN (...)` is NULL, which `IF` reads as false - so the role checks `COALESCE`; and Supabase's default privileges grant EXECUTE on new `public` functions to `anon`/`authenticated`, so the shared `link_player_account` helper is explicitly REVOKEd. `supabase/scripts/player-accounts-checks.sql` re-checks every rule inside a rolled-back transaction (safe on prod). **That's Me!** (`linked_account`) is inserted/deleted by the RPCs and also derived by `recomputeAllAchievements` from `player_accounts` (`unlocked_at = linked_at`, via `computeAchievementsForPlayer`'s `linkedAt`), so an admin Recompute keeps it; it **counts toward** Achievement Hunter/Completionist. Because of that, each link change recomputes from the browser (`supabase.ts`): a link non-destructively, an unlink after first deleting that player's three meta rows, since the recompute never deletes. The admin Recompute reads the links (like players and matches) **before** it deletes every row, and hands them to `recomputeAllAchievements` - a read failing after the delete would leave the table empty. **Release order:** apply `20260927_player_accounts.sql` before the frontend or `calculate-elo` that reads `player_accounts` reaches that environment
- `banners` - marquee announcements: message, optional `starts_at`/`ends_at` window, `is_active` master switch, `audience` (`everyone` | `members`), `season_id` on the one a season start created (unique, so the trigger is idempotent), and `release_version` on a release announcement (unique - one per release; its text is stored literally, so it adds no NULL-message case). `message` is nullable *only* when `season_id` is set (`banner_message_present`), which is how "use the translated default" is stored. SELECT is deliberately wider than "currently live": future-scheduled rows are readable so an already-open client can reveal one the moment its window opens (nothing changes in the DB at that instant, so no realtime event would trigger a refetch). Hidden and expired rows are admin-only, and `members` rows are never sent to anonymous callers. An `AFTER INSERT` trigger on `seasons` (`create_season_banner`) adds the 14-day season announcement
- `seasons.planned_end_at` (optional, `CHECK > started_at`, set when starting a season or edited on the running one through the admin UPDATE policy), `seasons.voting_opened_at` (set only by `open_award_voting`: admin, running season only, server time, idempotent, no undo) and `seasons.voting_closes_at` (optional, `CHECK > started_at`; the admin's closing date, replacing the 14-days-into-the-next-season default either way; edited through the admin UPDATE policy, or set to server time by `close_award_voting` - admin, only while that season's ballot is open, otherwise `voting_not_open`)
- `season_award_votes` - the secret ballot (#121): `(season_id, award_id, voter_user_id)` PK → `nominee_player_id`, `updated_at`. **SELECT is your own rows only - deliberately no admin clause**, so nobody reads anyone else's votes, admins included; #122 tallies inside a SECURITY DEFINER function. No write policies and INSERT/UPDATE/DELETE revoked from `anon`/`authenticated`: the only write path is `cast_award_vote(season, award, nominee | NULL)` (`user`/`admin`, linked, window open, not yourself, nominee eligible; NULL clears; a closed ballot can't be cleared either). It raises bare codes: `not_allowed`, `voter_not_linked`, `unknown_award`, `voting_not_open`, `self_vote`, `nominee_not_eligible` (and `season_not_active` from `open_award_voting`). `award_turnout(season)` (`user`/`admin`) returns counts only - `{voters, eligible, awards: {id: n}}`, eligible = linked user/admin accounts - for the ballot and nudge; **the per-nominee tally deliberately waits for the close (#122)**, since live standings in a league this small let a watcher diff out individual ballots and invite tactical switching while picks can still change. The window and eligibility live in the internal helpers `award_voting_is_open` and `award_nominee_eligible` (EXECUTE revoked from `authenticated` too), which #122's finalisation reuses. Deleting a player cascades their nominations; unlinking or demoting a voter keeps their votes. `supabase/scripts/season-award-voting-checks.sql` re-checks every rule inside a rolled-back transaction. **Release order:** `20260930_season_award_voting.sql` before the frontend (the old frontend keeps working - the new `end_season_and_start_new` argument defaults to NULL)
- `team_names` - optional name + 2 aliases + color per canonical player pair (player_id_lo < player_id_hi); stats derived at runtime in `teamUtils.ts`, not stored; only teams with ≥ 2 matches are shown

### Elo Calculation

The math lives in **`supabase/functions/_shared/elo.ts`, mirrored byte-for-byte into `frontend/src/lib/elo.ts`** (the edge function runs on Deno and isn't reachable from the Vite build, same as the achievements pair). `diff` the two to check for drift. Everything else - the edge function, its tests, and the match form's preview - imports from one of those two copies, so what the form projects and what gets written can't disagree.

- **A recorded match is a series of N games**, and it is rated on its *margin*: `d = |a − b|`, then `ΔR = K · d · (S − E)` with `S` 1 for the winning side and 0 for the losing one. Equivalently, the tally is reduced to a `d:0` sweep - a 2:1 counts as a 1:0, a 3:1 as a 2:0, drawn pairs of games cancelling out. E is taken once from the pre-series ratings, so the result is independent of the order the games were played in. Two consequences: **winning a series can never cost you rating** (`K·d·(1 − E)` with `E < 1`), and the game count contributes nothing - a 5:4 grind rates identically to a 1:0. The latter is the deliberate price; if sessions ever get long enough for it to bite, a sub-linear discount on `d` in `rateSeries` is where it would go.
- **Why margin and not FIDE.** Until 2026-09 this summed per-game residuals (`ΔR = K · Σ_games(S − E)`), which is right when the game count is fixed in advance and independent of the results - a tournament. A lunch-break league is not that: people play until someone is clearly ahead or until the hour ends, a stopping rule that *depends on* the margin, under which the game count says nothing about who is stronger. The old model's visible symptom was a heavy favourite going −60 for winning 3:2. Note the switch needed **no `k_factor` change**: the two models agree exactly on every sweep and everywhere all four ratings are equal (both reduce to `K·(w − l)/2` there), so only non-sweeps between unequal teams moved. Season 4, the only season recorded under the old model, was re-rated under margin on 2026-09-16 with `supabase/scripts/rerate-season/` (see below), so no stored rating reflects the old model any more.
- **Partner weighting** (`seasons.partner_weight`, default 0.25): each player's rating is pulled that far towards their partner's *before* expectations are computed. `w = 0` ignores the partner (the pre-2026-08 behaviour, where a 1900+1100 pair beating two 1500s gave `+2.91` and `+29.09` for one identical event); `w = 0.5` collapses both onto the team average, giving both partners the same delta; the default sits between, your own rating counting triple. The dialog also offers the 1/3 the league ran on before 2026-08-03. Per season like `k_factor`, so it is re-tunable at a season boundary without a deploy. Written as `0.25`, not `1/4`: the column is `NUMERIC(4,3)`, which stored 1/3 as `0.333` - a value that no longer equalled `DEFAULT_PARTNER_WEIGHT` on the way back.
- **The four deltas sum to exactly zero.** This holds because each player's E is the *average of their pairwise expectations* (linear, and pairwise expectations are complementary), so the four E values always total 2 - and the margin puts `2·d` on the table (`d` to each of the two winners), which is exactly `d · ΣE`. Two easy ways to break it: averaging the opponents' **ratings** instead of their expectations (the logistic isn't linear), or blending only your own team and leaving the opponents raw. Rounding also happens once across all four (`roundPreservingSum`), or each delta rounding on its own would leak up to 2 points per match.
- **`k_factor` is per margin point, not per recorded match.** Season 2026-08 runs at K=48, which is not the cut from the old 64 it looks like: under the one-event-per-match model an even session moved a flat ±32, whereas K=48 gives ±48 for an even 2-0 and ±24 for an even 2-1 or 3-2. Read the season K with that in mind before comparing it to a pre-series season. It is also the lever to reach for if long series feel too swingy - the margin model deliberately left it untouched.
- **Season Elo used for math**: the function fetches `player_season_stats.current_season_elo` for the 4 players and rates on those. The resulting delta is then applied to `players.current_elo` (all-time). This ensures all players start equal (1500) at the beginning of each season.
- `elo_history` always stores all-time Elo values (`elo_before`/`elo_after`); season-normalized display is derived in the frontend using `1500 + (alltime - elo_at_start)`
- **Win/loss is read from `elo_history.won`, never from the sign of `elo_change`.** Margin scoring makes a winner's delta non-negative again, but not *positive* - it rounds to 0 across a wide enough gap, so a winning row with `elo_change = 0` is legitimate. `frontend/src/lib/eloHistory.ts` (`didWin`/`didLose`) is the only place that decision is made; it falls back to the old sign rule for rows where `won` is null (inactivity penalties, and anything written between the migration and the function deploy). Achievements were always safe here because they read `matches.winning_team`.
- **Re-rating a season** is `supabase/scripts/rerate-season/`: `export.sql` snapshots the active season (read-only), `rerate.ts` replays it under the current `rateSeries` and writes one SQL transaction. Two guards are the point of it. The replay first re-runs the season under the *old* sum-of-residuals model and must reproduce every stored row exactly, or it refuses to write SQL (`--allow-drift` overrides) - that is what proves its reading of starting ratings and chronology is right. And the SQL embeds every old value it read and aborts inside the transaction if any has moved, so a match recorded after the snapshot, or applying the file twice, writes nothing. It refuses seasons with inactivity-penalty rows (not replayable yet) and players without a season row. Deleting a match leaves later rows chained to the deleted result (`deleteMatch` only recomputes the players' totals), which shows up here as drift. Follow it with Admin → recompute achievements, since some read rating history
- `players.wins/losses` and `player_season_stats.wins/losses` count **series, not games**, so one recorded match stays one result everywhere else in the app
- On match record: updates player ELOs, writes to `elo_history`, then calls `recomputeAllAchievements` from `supabase/functions/_shared/achievements.ts`
- Shared achievements logic lives in `_shared/` so it can be imported by both the edge function and tests

### Releases
Versioned with changesets (v3). The versioned package is `toegg-elo-frontend` (private); its `version` **is** the app version, shown as the `vX.Y.Z` chip beside the header title (Vite `define` - a running dev server keeps the value it started with, so restart it after a bump). **Numbering: 1.0.0 is the seasons release (2026-04-04)**; earlier history is 0.1-0.6. `frontend/CHANGELOG.md` was seeded by hand from the PR history and is plain markdown - entries can be reworded or regrouped at any time.

- **Version PR:** on every push to `main` with pending changesets, `.github/workflows/release.yml` (`changesets/action`) opens/updates "Release: version packages", running the root `version-packages` script: `changeset version`, then `frontend/scripts/stamp-changelog-date.mjs` dates the newest heading (changesets writes the heading itself). That PR is created with `GITHUB_TOKEN`, so CI doesn't run on it.
- **Tag + GitHub Release:** on a push with **no** pending changesets (i.e. merging the Version PR), the workflow tags `vX.Y.Z` and creates the GitHub Release from the newest changelog section with `gh` - not `changeset git-tag`, whose v3 output lacks the `New tag:` lines `changesets/action` parses. It only tags when the CHANGELOG's newest heading equals the package version, and skips an existing release, so every later push is a no-op.
- **Folding a change into the current release** instead of bumping: add its entry under the newest heading by hand and ship it without a changeset (how #127 went into 1.10.0). Keep headings as `## x.y.z (yyyy-mm-dd)` - the parser, the date stamp and the tag step all read them.
- The workflow sets `HUSKY: "0"`: `changesets/action` commits the Version PR itself, and the pre-commit hook needs `deno`, which the runner doesn't have.
- **Announce** (Admin → Message Banner) creates the release banner for the running build; needs `20260926_release_banners.sql` (applied on staging and prod).

### Theming

Three themes selectable via a ☀️/🌙/🪟 toggle in the header; choice saved in cookie `toegg-theme`.

- **Light** (default) - existing design unchanged
- **Dark** - CSS variable overrides on `[data-theme="dark"]`; hardcoded `white` backgrounds in dialogs overridden via `[data-theme="dark"] .bg-white`
- **Win95** - teal desktop + custom Win95 window chrome (`Win95Shell`); uses `@react95/core` (v9) for Win95 CSS variables/theming imported via `@react95/core/themes/win95.css`; component styles overridden via `[data-theme="win95"]` in `App.css`

**Win95 dialogs** are styled entirely from CSS off one `modal-panel` hook class, which all four modals (PlayerDetail, TeamDetail, PlayerModal, SeasonDialog) carry. Their first child is already the heading - either the `<h2>` itself or a header row holding it plus a close button - which is exactly a title bar's shape, so `[data-theme="win95"] .modal-panel > :first-child` becomes one. That is why no dialog contains Win95-specific markup, and why a new dialog only needs the class. The panel padding is normalised to the 3px window frame so the title bar's full-bleed has a single value to cancel.

**Achievements flyout in Win95**: the overview's details tooltip normally flies out to the right of a row. Win95 is the one theme where `main` has no max-width, so the card fills the whole 1600px window and a row's right edge *is* the window's edge - the flyout lands outside and is clipped by the shell's `overflow: auto`. Fixed by dropping it below the row instead, reusing the same treatment the `max-width: 768px` case already uses for the same reason (no room to the side). Card widths are deliberately left alone: constraining the card or the rows to reserve space either shrinks Achievements below every other tab or leaves a dead band between the table and the card border.

**`--control-h`** is the shared height for the compact controls that share a card's header row (season select, `.lb-toggle` segmented toggles, `.player-ac--compact`). They each used to pick their own padding and so lined up at three different heights; anything new on such a row should use it too.

`ThemeProvider` must wrap `AuthProvider` in `main.tsx`. Do **not** use react95's `Modal` component as the window frame - it attaches drag event listeners that break inner click handlers; `Win95Shell` uses plain HTML instead.
